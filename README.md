# cg-us

Обёртка над [CHAPERONg](https://github.com/abeebyekeen/CHAPERONg) для расчёта
свободной энергии связывания белок-пептидных комплексов методом umbrella
sampling: манифест на входе, PMF-профили, статистика по репликам и сверка с
экспериментом на выходе.

Установка окружения — [INSTALL.md](INSTALL.md).

## Зачем нужна обёртка

CHAPERONg умеет вести US-пайплайн от PDB до `gmx wham`, но:

* он полностью интерактивный (`read -p` на каждом шаге) — прогнать 6 систем × 3
  реплики руками нереально;
* он считает **одну** реплику в одной рабочей папке, без статистики по повторам;
* `gmx wham` он вызывает без бутстрапа, без отбрасывания уравновешивания и без
  оценки перекрытия гистограмм;
* он ничего не знает про экспериментальные аффинности.

`cg-us` закрывает ровно эти дыры и не переписывает то, что CHAPERONg уже делает.

## Что делает пакет

**Подготовка.** Читает манифест, режет PDB по цепям мишени и байндера,
поворачивает комплекс так, чтобы вектор COM(мишень)→COM(байндер) смотрел вдоль
`+z`, считает вытянутый вдоль `z` бокс под всю длину вытягивания, детектирует
head-to-tail замыкание и дисульфиды, генерирует полный набор `.mdp` и
`paraFile.par`.

**Запуск.** Два взаимозаменяемых бэкенда:

| | `chaperong` | `direct` |
|---|---|---|
| чем считает | `run_CHAPERONg.sh`, стадии 0→18 | собственные вызовы `gmx` в той же последовательности |
| управление | `pexpect`, ответы по шаблонам промптов | обычный `subprocess` |
| окна | последовательно | пул воркеров (`run.window_workers`) |
| зависимости | grace, pymol, imagemagick | только GROMACS |
| рестарт | со стадии CHAPERONg | с любой стадии (`--start/--stop`) |

Оба оставляют после себя одинаковые артефакты (`tpr_files.dat`,
`pullf_files.dat`, `coordinates_SMD/`, `configuratns_list.txt`), поэтому анализ
у них общий, и одну систему можно посчитать одним бэкендом, другую — другим.

Две вещи, которые CHAPERONg оставляет пользователю, обёртка делает сама:
позиционные ограничения на «неподвижную опору» (`POSRES_TARGET`, только backbone
мишени) вписываются в `topol.top`, а `index.ndx` с группами `Target`/`Binder`
пишется по диапазонам атомов, вычисленным из `topol.top` — не через
`gmx make_ndx` вслепую, а по реальным moleculetype-блокам цепей.

**Анализ.** Свой прогон `gmx wham` с бутстрапом и отбрасыванием первых
`umbrella.discard_ns` из каждого окна, метрики качества выборки, статистика по
репликам, регрессия против эксперимента, графики, HTML-отчёт.

## Манифест

CSV, минимально — четыре колонки:

```csv
pdb,name,target,binder
1ycr_mdm2_p53.pdb,mdm2_p53,A,B
```

Все остальные колонки опциональны и используются, если есть:

| колонка | смысл |
|---|---|
| `role` | `benchmark` или `negative_control` (контроли исключаются из регрессии и проверяются на порог) |
| `kd_exp_M` | Kd в молях; если нет `dg_exp_kcal_298K`, ΔG считается как `RT ln Kd` |
| `dg_exp_kcal_298K` | готовая ΔG, приоритетнее Kd |
| `assay_T_K` | температура пересчёта Kd→ΔG (по умолчанию 298.15) |
| `affinity_type` | `Kd`, `Ki`, …; для не-Kd в отчёт попадает предупреждение |
| `sim_ph` | пишется в метаданные системы |
| `restrain_binder` | 1 — мягкие CA-ограничения на байндер **только на этапе уравновешивания** (NVT/NPT до SMD); в pull и в окна US они не попадают, иначе позиционные ограничения работали бы против вытягивающей силы и искажали PMF |
| `cyclic_type`, `binder_seq`, `caveats` | попадают в отчёт как есть |

Проверить манифест до запуска:

```bash
cg-us validate --manifest bench6/manifest.csv
```

## Использование

```bash
cg-us prep    --manifest bench6/manifest.csv --root runs/bench6 \
              --protocol protocol.yaml --ff-dir ~/ff/charmm36-jul2022.ff
cg-us run     --root runs/bench6                      # все системы, все реплики
cg-us run     --root runs/bench6 --system mdm2_p53 --replica 2
cg-us extend  --root runs/bench6 --dry-run            # какие окна недобрали
cg-us extend  --root runs/bench6                      # продлить только их
cg-us analyze --root runs/bench6
```

`cg-us all` делает то же самое одной командой.

Повторный `run` возобновляемый: реплики с непустым `tpr_files.dat` пропускаются
целиком, а если на диске уже есть `pull.gro` (steered MD досчитан), CHAPERONg
перезапускается сразу со стадии 14 — подготовка, уравновешивание и SMD заново не
считаются. Принудительно: `--force` (всё заново) или `--from-stage 0|14`.

Стадия 13 (ролик SMD-траектории) управляется `run.skip_movie`; зависимости и
подводные камни PyMOL/ImageMagick — в [INSTALL.md](INSTALL.md), раздел 4.1.

Дерево результатов:


## Контакты интерфейса

`cg-us contacts --root runs/X [--system ...] [--replica N] [--source windows|smd|both]` считает контакты мишень–бейндер по типам GetContacts (H-связи остов–остов, боковая–остов, боковая–боковая; солевые мостики; пи–катион; пи-стэкинг; т-стэкинг; гидрофобные; ван-дер-ваальсовы) по кадрам окон umbrella (равновесные, по одному состоянию на окно) и по SMD-пуллу (неравновесный, кадры по интервалам расстояния).

Результат для каждой реплики: `analysis/contacts_<источник>_counts.csv`, `..._pairs.csv`, `.json` (контакты в связанном состоянии, расстояние потери половины контактов, «горячие» остатки, контакты в конце пути). Для рана: `analysis/contacts_summary.csv` и картинки `contacts_<система>_<источник>.png`. Если на последних 0.3 нм пути ещё остаются контакты, выводится `PULL INCOMPLETE`: пулл не довёл разрыв до конца. Нужен `pip install 'cg-us[contacts]'` (MDAnalysis). Водные мостики не считаются. Команда ставится в очередь: `--enqueue`.

## Очередь ClearML

Команды `prep`, `run`, `extend`, `analyze`, `all`, `bench` можно не запускать сразу, а ставить в очередь ClearML: добавьте `--enqueue`. Агент очереди берёт по одной задаче, поэтому задачи идут друг за другом и не делят между собой GPU и ядра; очередь и консольный лог видны в веб-интерфейсе ClearML.

```bash
pip install 'cg-us[queue]'        # один раз: ставит clearml (credentials берутся из ~/clearml.conf)

cg-us run     --root runs/gdf8 --manifest manifest_gdf8.csv --enqueue
cg-us extend  --root runs/gdf8 --fill-gaps --enqueue
cg-us analyze --root runs/gdf8 --bootstraps 0 --system gdf8_df3 --enqueue
cg-us queue status                # что идёт и что ждёт, в порядке запуска
```

* Проект передаётся отдельным аргументом: `--project GP20181` (по умолчанию `$CGUS_CLEARML_PROJECT`, иначе `GP20181`). Задачи раскладываются по папкам `<проект>/Umbrella sampling/run`, `.../analysis` и `.../extend` (`prep`, `all`, `bench` попадают в `run`).
* Очередь: `--queue NAME` (по умолчанию `$CGUS_CLEARML_QUEUE`, иначе `a100-1`). Название задачи: `--task-name TEXT`. `--queue` и `--project` сами по себе тоже включают `--enqueue`.
* Задача запускает тот же `cg-us`, что и поставил её в очередь (тот же интерпретатор, рабочая папка и `PATH` с gmx), окружение агент не пересобирает и его настройки не меняются.
* Очередь знает только о задачах ClearML: запущенное руками через `nohup` она не видит и под него не ждёт.

## Протокол

Всё в `protocol.yaml`, значения по умолчанию — в комплекте. Ключевое:

```yaml
replicas: 3
temperature: 310.0
prep:     {heavy_hydrogens: true, box_edge_xy: 1.0, box_edge_z: 1.0}
smd:      {rate: 0.001, k: 1000, time_ns: 2.0, dt: 0.004}   # 2.0 нм медленно
umbrella: {dense_spacing: 0.1, dense_until: 1.0, window_spacing: 0.2,
           time_ns: 3.0, extend_ns: 3.0, max_ns: 24.0, min_neff: 50,
           equil_ns: 0.5, discard_ns: 0.5, max_distance: 2.0, dt: 0.004}
wham:     {bootstraps: 200, method: b-hist, unit: kCal}
run:      {backend: chaperong, ntomp: 8, gpu: true, window_workers: 1}
analysis: {plateau_width: 0.4, overlap_min: 0.03, control_threshold: -5.0}
```

Такие настройки дают 16 окон: 0.1 нм до `dense_until` и 0.2 нм в хвосте. Если
минимальное перекрытие гистограмм в отчёте меньше `overlap_min`, уменьшайте шаг
или поднимайте `umbrella.k`. Если после `cg-us extend` окна всё равно упираются в
`max_ns`, дело не во времени — смотрите на бимодальность гистограмм.

## Производительность

Стоимость расчёта — это `окна × нс × реплики`, и она растёт быстрее, чем кажется.
С исходными настройками (26 окон × 20 нс × 3 реплики) одна система — это 1560 нс,
то есть ~90 ГПУ-часов даже при вполне здоровых 500 нс/сутки.

Перед запуском продакшна померьте своё железо:

```bash
cg-us bench --root runs/bench6 --system actrIIb_bimagrumab_cdr3 --steps 10000
```

Команда берёт готовый `.tpr` из папки реплики, прогоняет короткие mdrun с разными
комбинациями разгрузки на GPU, затем запускает несколько окон одновременно и
печатает суммарную пропускную способность. Результат — `analysis/benchmark.csv`
и оценка часов на систему для вашего протокола.

Что даёт выигрыш, по убыванию важности:

| Приём | Множитель | Как включить |
|---|---|---|
| GPU-resident режим (`-update gpu` + PME и bonded на GPU) | 1.3–2× | `run.gpu_update/gpu_pme/gpu_bonded` (по умолчанию включены) |
| Несколько окон на одной GPU | 2–3× | `run.window_workers: 4`, бэкенд `direct` |
| Подбор числа потоков под разгрузку | 1.1–1.4× | `run.ntomp`, ветка `bench` по ntomp |
| HMR + шаг 4 фс | ~2× | `prep.heavy_hydrogens: true`, `dt: 0.004` |
| 3 нс базы вместо 20, с адресным продлением | до 6× | `umbrella.time_ns` + `cg-us extend` |
| Переменный шаг окон (0.1 нм у минимума, 0.2 нм в хвосте) | ~1.4× | `dense_spacing`/`dense_until`/`window_spacing` |
| Бокс: отступы 1.0 нм вместо 1.2/1.5, путь 2.0 нм вместо 2.5 | ~1.3× | `prep.box_edge_*`, `umbrella.max_distance` |

Размер бокса вдоль оси вытягивания считается по двум условиям, и решающим бывает
не то, которое кажется очевидным: помимо геометрии (молекулы разъехались плюс
сольватная подушка) GROMACS требует, чтобы расстояние между COM групп не
превышало `0.49 × box_z`. Итоговое расстояние равно **начальному** `d0` плюс длина
вытягивания, а не только длине вытягивания — для компактных комплексов с большим
`d0` именно это условие и связывает. Сверх этого закладываются два запаса: `prep.pull_headroom` (0.5 нм) — на дрейф
`d0` за время сольватации и уравновешивания плюс тепловые колебания в крайнем
окне (±4σ, где σ = √(kT/k) ≈ 0.05 нм при k = 1000), и `prep.pull_box_margin` (4%)
— на сжатие бокса при NPT. `cg-us prep` печатает, какое условие сработало и
сколько нанометров вытягивания бокс реально выдержит.

Оценка `d0` берётся с кристаллической структуры и после уравновешивания
устаревает, поэтому перед SMD запускается проверка по факту: измеряется реальное
COM-расстояние в `npt.gro` и реальный `box_z`, и если полной длины не хватает,
`md_pull.mdp` укорачивается, а эффективная длина пишется в `pull_range.json` и
используется при отборе окон. В бэкенде `chaperong` проверка висит на промпте про
custom index — это единственная точка между NPT и grompp вытягивания.

Значения по умолчанию в `protocol.yaml` уже включают всё перечисленное: 16 окон ×
3 нс × 3 реплики = 144 нс на систему вместо 1560, то есть в 10.8 раза меньше
работы ещё до всякой разгрузки на GPU.

### Сколько времени нужно окну

Равномерное время на окно — почти всегда неверное распределение. Окна в
сольватированном хвосте декоррелируют за пикосекунды, окна в области десольватации
и разрыва контактов могут оставаться скоррелированными сотни пикосекунд. Поэтому
базовый проход короткий, а время добавляется адресно:

```bash
cg-us extend --root runs/bench6 --dry-run   # показать план, ничего не считая
cg-us extend --root runs/bench6             # продлить только дефицитные окна
```

Критерий — не «сколько наносекунд», а сколько в окне **независимых** отсчётов.
Для каждого окна по `pullx.xvg` считается статистическая неэффективность
`g = 1 + 2Σρ(t)` (оценка Соколя с автоматическим окном), из неё
`N_eff = n / g` и время автокорреляции. Окно продлевается, если:

* `N_eff < umbrella.min_neff` (по умолчанию 50), или
* среднее ξ уезжает между половинами больше чем на `max_drift_sd` стандартных
  отклонений, или
* гистограмма окна бимодальна — это отдельный флаг: он означает медленную
  ортогональную степень свободы, и добавление времени такое окно чинит не всегда.

Продление делается через `gmx convert-tpr -extend` + `mdrun -cpi -append`, то есть
дописывает ту же траекторию, а не начинает новую. Потолок на окно —
`umbrella.max_ns`; упёршиеся в него окна отмечаются отдельно, чтобы их не пропустить.

Диагностика попадает в `window_diagnostics.csv` рядом с репликой, в таблицу реплик
(`sampled_ns`, `n_eff_min`, `under_sampled`) и на график
`analysis/<система>/window_sampling.png` — там сразу видно, какие окна дорогие.

### Процессорные ядра

`run.ntomp` — потолок на весь mdrun (`-ntomp`), `run.ntmpi` — число thread-MPI
рангов. При `ntomp: 8` расчёт видит восемь ядер независимо от того, сколько их на
узле. Значение `0` означает «взять все».

Больше — не всегда лучше. При полной разгрузке (`-nb/-pme/-bonded/-update gpu`)
на CPU почти ничего не остаётся, и лишние OpenMP-потоки только добавляют
синхронизации; оптимум обычно 4–8. Зато если PME остаётся на CPU, ядра дают
почти линейный прирост. `cg-us bench` перебирает `ntomp` (4, 8, половина ядер,
все ядра) отдельно для каждой комбинации разгрузки — по таблице сразу видно, в
какую сторону двигаться.

При `window_workers > 1` бюджет ядер делится между окнами: каждому достаётся
`cpu_cores // window_workers` потоков, и каждое окно прижимается к своему
диапазону ядер (`-pin on -pinoffset`). Без этого четыре окна по восемь потоков на
шестнадцатиядерном узле дрались бы за одни и те же ядра и считались медленнее,
чем по очереди. Заданный `ntomp` при этом работает как потолок, а не как
требование.

Ещё одна причина, по которой короткая база работает: вытягивание замедлено с
0.005 до 0.001 нм/пс. Быстрый SMD оставляет напряжённые стартовые конфигурации,
которые потом приходится долго релаксировать в каждом окне; медленный стоит
лишние 1.5 нс на реплику и экономит их в шестнадцати окнах.

Три оговорки:

* **Окна параллелит только бэкенд `direct`.** CHAPERONg считает их строго
  последовательно, и обойти это, оставаясь внутри его цепочки, нельзя. Для
  продакшна имеет смысл `backend: direct`, а CHAPERONg держать для одной
  референсной реплики.
* **HMR меняет массы водородов.** Для равновесной выборки и свободных энергий это
  стандартная и валидированная практика, но кинетику и колебательные спектры на
  таких траекториях считать нельзя. Отключается `prep.heavy_hydrogens: false` —
  тогда обязательно верните `dt: 0.002`, иначе `cg-us prep` откажется стартовать.
* **`-update gpu` несовместим с *constraint* pulling**, но наш bias силовой
  (`pull-coord1-type = umbrella`), так что ограничение не задевает. Если сборка
  всё же откажется, и обёртка, и шим спускаются по лестнице разгрузки на ступень
  вниз и пишут об этом в лог.

## Циклические пептиды

Начиная с GROMACS 2021.1 `pdb2gmx` сам определяет head-to-tail замыкание: если
расстояние между N первого остатка и C последнего попадает между `-sb`
(по умолчанию 0.05 нм) и `-lb` (по умолчанию 0.25 нм), кольцо замыкается.
Дефолтный `-lb` тесноват, поэтому cg-us передаёт `-sb 0.05 -lb 0.4`:

```yaml
prep:
  cyclic_sb: 0.05
  cyclic_lb: 0.4
  cyclic_lb_conservative: 0.25
  cyclic_lb_from_manifest: true
```

Тот же интервал используется и для детекции при подготовке, так что отчёт
показывает ровно то, что сделает pdb2gmx, а не отдельную эвристику.

**Почему `-lb` не глобальный.** Расширение окна до 0.4 нм задевает не только
настоящие циклопептиды. В bench6 у `5ngv` (CDR-H3 графт, замкнутый дисульфидом,
а не по остову) N–C = 3.64 Å — попадает в окно, и pdb2gmx сшил бы свободные
концы. Поэтому при `cyclic_lb_from_manifest: true` колонка `cyclic_type`
управляет порогом:

| `cyclic_type` | `-lb` |
|---|---|
| содержит «head-to-tail» или «backbone» | 0.4 нм |
| пусто (нет данных) | 0.4 нм |
| что-то другое («linear», «disulfide-cyclised …») | 0.25 нм |

Клампинг попадает в `prep.json` и в предупреждения — но только когда он реально
меняет исход, то есть когда N–C лежит между двумя порогами. Чтобы отключить и
применять 0.4 нм ко всему, поставьте `cyclic_lb_from_manifest: false`.

**Как флаги доходят до pdb2gmx.** В бэкенде `direct` они добавляются в командную
строку напрямую. CHAPERONg собирает вызов `pdb2gmx` сам, поэтому в каждую папку
реплики кладётся шим `gmx_cgus.sh`, который прописывается в `paraFile.par` как
`gmx_exe`: он дописывает `-sb`/`-lb` только к `pdb2gmx`, а все остальные
подкоманды пробрасывает без изменений. `-sb`/`-lb` описаны в DESCRIPTION
`pdb2gmx`, но отсутствуют в таблице опций (скрытые), поэтому оба пути при ответе
«Unknown command-line option» повторяют запуск без них и пишут предупреждение.

## Что считается

**На реплику:**

* ΔG = PMF(минимум) − PMF(плато), плато = среднее по последним
  `plateau_width` нм профиля; шероховатость плато сообщается отдельно как
  признак того, что связывание не разошлось до нуля;
* бутстрап-ошибка ΔG из `gmx wham -nBootstrap` (`b-hist`);
* положение связанного состояния ξ, барьер разъединения;
* коэффициент перекрытия соседних окон
  `OVL = Σ min(p_i, p_j)`, минимум/медиана/число пар ниже порога;
* сходимость: ΔG по нарастающим блокам траектории и раздельно по первой и
  второй половине (`half_split_drift`);
* по SMD: максимальная сила, работа вытягивания, диапазон смещения.

**На систему:** среднее, SD, SEM, 95% CI (t-распределение), размах, CV, средняя
бутстрап-ошибка, флаги качества.

**Против эксперимента:** MAE, RMSE, систематический сдвиг (ME), максимальная
ошибка, Пирсон r и R², Спирмен ρ, Кендалл τ, наклон и свободный член регрессии,
а также попарная таблица ΔΔG с MAE и долей правильно предсказанных знаков —
для ранжирования это информативнее, чем абсолютные значения.

Контроли (`role: negative_control`) в регрессию не входят; для них проверяется
только `ΔG > control_threshold`, и результат выводится отдельной плашкой.

## Ограничения, о которых стоит помнить

* **Стандартное состояние.** ΔG из PMF по COM-расстоянию — это не ΔG°. Нет ни
  поправки на объём связанного состояния, ни ограничений на ориентацию
  (Woodak/Gilson-подобная схема здесь не реализована). Для ранжирования
  конгенерических пар это обычно неважно, для абсолютных чисел — важно. Опция
  `analysis.jacobian_correction` добавляет к PMF член `2kT ln ξ`, компенсирующий
  рост доступного объёма при изотропной выборке в несвязанном состоянии; по
  умолчанию выключена, включайте осознанно и не сравнивайте включённые и
  выключенные прогоны между собой.
* **Одна реакционная координата.** COM-расстояние вдоль `z` — плохая координата,
  если пептид уходит вбок или частично разворачивается. Смотрите на
  `plateau_roughness` и на разброс между репликами.
* **Ki ≠ Kd.** Для `trypsin_sfti` и `trypsin_mcoti` в bench6 экспериментальные
  величины — константы ингибирования; обёртка это помечает, но в регрессию их
  всё равно берёт.
* **Циклические пептиды.** Замыкание делает pdb2gmx (см. отдельный раздел ниже);
  cg-us только задаёт пороги и предупреждает. Проверяйте `topol.top` глазами
  хотя бы один раз на систему.
* **Реплики не независимы полностью.** Все окна одной реплики стартуют из одной
  SMD-траектории. Разброс между репликами занижает истинную неопределённость;
  это оценка воспроизводимости, а не полная погрешность метода.
